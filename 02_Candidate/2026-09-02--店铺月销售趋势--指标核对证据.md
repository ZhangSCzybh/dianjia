# 店铺月销售趋势：销售金额与销售数量核对证据

## 结论

1. `saleNum` 的独立基线为 `sum(sale_deal_num - sale_refund_num)`。15 家有销售事实的店铺全部与 FlowBI 响应一致，合计均为 `460`。
2. 在本次确认的商户配置下，`saleMoney` 已建立并验证独立基线。15 家共同店铺全部在 `0.01` 容差内匹配；合计均为 `128287.6101`。
3. 当前配置为：剔除储值赠送支付、礼品卡赠送支付、抖音赠送支付；额外将“礼品卡”作为其他支付方式整体剔除；不剔除抖音平台补贴。因此礼品卡不能再只扣赠送比例，必须整体扣除。
4. FlowBI 另有 `yl01255` 的 `saleMoney=0, saleNum=0` 独有行，基线无相应事实行。请求虽包含非零过滤条件，仍应将此情况作为独立的行集合/过滤行为检查，不与指标金额正确性混为一谈。

## 已验证 SQL

目的：用 SKU 销售事实表计算净销售及数量，再用独立的商品-支付分摊表应用已确认的支付剔除配置。`FINAL` 与 `deleted=0` 必须保留，避免版本记录和软删除数据造成虚假差异。

```sql
WITH fact AS (
    SELECT
        storage_id,
        sum(sale_deal_money - sale_refund_money) AS raw_net_sale_money,
        sum(sale_deal_num - sale_refund_num) AS baseline_sale_num
    FROM flowretail.dm_order_sku_sale_bi_ds_10010 FINAL
    WHERE deleted = 0
      AND bill_date >= toDate('2026-08-01')
      AND bill_date < toDate('2026-09-01')
    GROUP BY storage_id
),
payments AS (
    SELECT
        storage_id,
        -- 配置：剔除储值赠送、抖音赠送；礼品卡整体剔除。
        sumIf(payment_reduce_money, payment_type = 101) AS stored_value_gift_deduction,
        sumIf(payment_reduce_money, payment_type = 118) AS tiktok_gift_deduction,
        sumIf(payment_money, payment_type = 110) AS gift_card_full_deduction
    FROM flowload.dm_order_item_sale_payment_ds FINAL
    WHERE brand_id = 10010
      AND deleted = 0
      AND bill_date >= toDate('2026-08-01')
      AND bill_date < toDate('2026-09-01')
    GROUP BY storage_id
),
stores AS (
    SELECT storage_id, code, name, area1_name, area2_name, area3_name, st_property_desc
    FROM flowload.dim_corp_storage_bi FINAL
    WHERE brand_id = 10010
      AND deleted = 0
)
SELECT
    '2026-08' AS dateYearMonth,
    s.code AS stCode,
    s.name AS stName,
    s.area1_name AS stArea1Name,
    s.area2_name AS stArea2Name,
    s.area3_name AS stArea3Name,
    s.st_property_desc AS stPropertyDesc,
    round(f.raw_net_sale_money, 4) AS raw_net_sale_money,
    round(ifNull(p.stored_value_gift_deduction, 0), 4) AS stored_value_gift_deduction,
    round(ifNull(p.tiktok_gift_deduction, 0), 4) AS tiktok_gift_deduction,
    round(ifNull(p.gift_card_full_deduction, 0), 4) AS gift_card_full_deduction,
    round(
        f.raw_net_sale_money
        - ifNull(p.stored_value_gift_deduction, 0)
        - ifNull(p.tiktok_gift_deduction, 0)
        - ifNull(p.gift_card_full_deduction, 0),
        4
    ) AS baseline_sale_money,
    round(f.baseline_sale_num, 2) AS baseline_sale_num
FROM fact f
INNER JOIN stores s ON f.storage_id = s.storage_id
LEFT JOIN payments p ON f.storage_id = p.storage_id
ORDER BY stCode;
```

## 关键金额差异

| 店铺 | 原始净销售 | 配置剔除项 | FlowBI / 基线 `saleMoney` |
| --- | ---: | --- | ---: |
| yldp | 8640.91 | 储值赠送 55.52 + 抖音赠送 0.17 | 8585.22 |
| ylyjmd | 1627.87 | 储值赠送 365.40 + 礼品卡整体 46.17 | 1216.30 |
| ylzbd | 1584.76 | 储值赠送 233.28 | 1351.48 |

注意：`payment_reduce_money` 不能对所有支付方式统一扣减。礼品卡被配置为“其他支付方式整体剔除”，其扣减项应为 `payment_money`；若同时扣 `payment_reduce_money`，会发生重复剔除。

## 自动化断言设计

将 FlowBI API 响应规范化为 `dateYearMonth + stCode` 粒度后，与基线做全外连接。每一行应输出：报表值、基线值、差额、缺失侧和原始成交/退款审计字段。

1. 数量硬断言：`abs(report.saleNum - baseline_sale_num) <= 0.01`。
2. 金额硬断言：`abs(report.saleMoney - baseline_sale_money) <= 0.01`。
3. 配置快照断言：运行前读取并存档销售金额的支付剔除配置；只要配置变化，就必须更新基线 SQL 的支付类型映射并重新用回归样本验证。
4. 行集合断言：报表独有、基线独有、以及 `0/0` 行分别列出；不要仅对合计断言。

## 配置变更风险

本 SQL 仅适用于本次截图所示配置与当前支付类型映射：储值卡 `101`、礼品卡 `110`、抖音代金券 `118`。若增加、取消或调整任一支付方式，先用 `yldp`、`ylyjmd`、`ylzbd` 这三家回归样本验证，再更新每日自动化基线。

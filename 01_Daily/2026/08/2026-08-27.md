## 2. 关键问题与解决方案

### 问题：上期销售金额到底取哪几天

**原因：** 周报中的“上期”与“同期”含义不同；环比应取上一周，同比应取去年同周。当前周未结束时，直接与完整上一周比较会造成偏差。

**解决方案：** 固定记录日期边界。周 35 为 2026-08-24 至 2026-08-30，环比周 34 为 2026-08-17 至 2026-08-23；周累计比较则按相同已过去天数对齐。

**最终结论：** 报表必须明确采用“完整自然周”还是“截至当天周累计”口径，不能混用。

### 问题：同一批订单在不同 SQL 中被归为会员或非会员

**原因：** 上一段 SQL 的会员维表限制了当前店铺，导致归属其他店铺的品牌会员无法 Join；新 SQL 去掉了店铺限制，按品牌范围识别会员。

**解决方案：** 对比会员维表 Join 条件、会员判断字段和数据源；逐订单核对 `custom_id`、手机号及会员归属店铺。

**最终结论：** 若业务定义是品牌会员，会员维表应按 `brand_id` 和有效状态关联，不应额外限制会员归属店铺；当前两笔订单应计为会员。

### 问题：非会员单数少于非会员订单数

**原因：** 单效单数只统计有效成交金额不为 0 的订单。金额为 0 的订单虽有订单 ID，但 `sell_order_num=0`，不会计入单数。

**解决方案：** 按订单展开核对金额、退款、统计类型和 `sell_order_num` 计算条件。

**最终结论：** 两个有效订单金额为 1043.12 元和 419.12 元，合计 1462.24 元；另一个 0 元订单不计入单数，因此单效单数为 2。

## 3. 知识沉淀

### SQL / 数据库知识

- ClickHouse 品牌专属销售表形如 `flowretail.dm_order_sku_sale_bi_ds_<brand_id>`；明细表 `flowload.dm_order_item_sale_bi_ds` 使用 `FINAL` 可核对替换合并后的结果。
- 销售净额常用公式为 `sale_deal_money - sale_refund_money`；成交金额和净销售额必须区分。
- 明细表一行通常是商品明细，不应把 `id` 直接当作明细唯一键；应使用 `data_fingerprint` 或 `item_id` 检查重复，订单数用 `uniqExact(id)`。
- 日期条件推荐使用半开区间：`bill_date >= '2026-08-15' AND bill_date < '2026-08-22'`，避免时间边界漏数。

### BI / 数仓知识

- 报表链路应按源表、ETL、原始数据集、普通数据集、组件、面板逐层对账。
- Join 前必须确认粒度；订单主表与商品明细一对多关联后直接 `sum` 主表金额会造成金额放大。
- “上期”通常表示上一周期，“同期”表示去年同周期；周累计同比/环比必须按已过去天数对齐。

### 测试经验

- 报表测试至少覆盖：记录数、金额、订单数、退款、时间边界、空数据、重复消费、跨店权限和页面/API/数据库一致性。
- 会员分类不能只看 `custom_id` 是否大于 0，也不能默认手机号为空就是真非会员；必须确认业务定义和会员维表 Join 范围。
- 对异常指标应先做订单级下钻，再判断是业务现象、Join 丢失、字段口径还是重复数据。

### AI 应用经验

- 可以让 AI 直接执行只读 SQL，完成表定位、字段核对、订单下钻和报表基准值计算；但必须先提供指标口径，SQL 可执行不代表业务正确。
- 数据库凭据不应写入总结、SQL、代码或截图；连接探测只报告成功/失败，不输出密码。

### 项目业务知识

- 店家系统包含 HR、SCM、ERP、零售、批发等数据源，经 FlowET 和 DTS/FlowDTS 汇入阿里云 ClickHouse，再由 FlowAPI/FlowBI 提供报表、标签和业务数据服务。
- 品牌 15056 重庆万象城店的会员资料可能归属其他店铺，但仍属于品牌会员；店铺归属与购买门店不是同一概念。
- 期初库存需要区分系统跑数 `biz_type=-1` 与进销存跑数 `biz_type=-2`；同一业务键重复记录应作为数据问题排查。
- 成本指标必须区分标准成本和总部综合成本，并验证 SKU/SPU 兜底及总部综合成本 CASE 优先级。
- 费用分摊比例按同门店同一天全部费用作分母，净利润需同时扣除成本和分摊费用。
- `pay_status`、预售 `bill_status`、`order_status` 是三套不同状态码，测试时不能混用。

## 4. 项目经验

项目：店家数据架构与销售 BI 报表

模块：零售销售、会员分析、周销售报表、ClickHouse 数仓

涉及业务：门店销售金额、会员/非会员销售、退款、单效单数、同比环比

关键逻辑：源订单明细按成交金额减退款金额形成单效销额；通过会员维表识别客户，再按门店和业务日期聚合；订单单数根据有效成交/退款条件计数。

风险点：会员维表按店铺过滤造成 Join 丢失；明细 Join 放大金额；完整周与周累计口径混用；退款和零金额订单影响单数；多集群数据可能漏查。

测试关注点：先确认指标口径，再做源表到报表逐层对账；校验唯一性、Join 基数、日期边界、退款、权限隔离、`FINAL` 前后结果及页面/API/SQL 一致性。
